# Contract: 工具执行链路

**Feature**: `005-tool-system`

## 1. 固定执行顺序（不变式）

```text
1. 按名取工具（取不到 → 失败）
2. 解析入参（解析失败 → 失败）
3. 前置校验（白名单；各类工具校验各自维度）
4. 执行（真正的副作用发生在这一步）
5. 写审计并返回结果
```

**硬约束**：

- 第 3 步**永远早于**第 4 步；校验不通过时第 4 步的副作用次数**必须为 0**。
- 第 1、2、3 步任一失败，都必须返回**不可重试**的失败结果。
- 顺序不得靠"代码评审目测"确认，必须由**调用顺序断言**钉死（`InOrder`）。

## 2. 副作用维度与校验对应

| 工具类别 | 校验维度 | 越界时的表现 |
|---|---|---|
| 文件类 | 路径 | 拒绝；**文件未被读取、未被写入** |
| 命令类 | 命令 | 拒绝；**没有任何进程被启动** |
| HTTP 类 | 域名 | 拒绝；**没有网络请求发出** |
| 外部服务工具 | 交由外部服务自行约束 | 本特性不额外加校验点，但调用同样经本链路 |

**空清单即全拒**：任一维度清单为空时，该维度**一律拒绝**（fail-closed）。

## 3. 失败语义契约

| 情况 | 结果 | 可重试 |
|---|---|---|
| 执行成功 | 成功 + 内容 | — |
| 工具名不存在 | 失败 + 原因 | 否 |
| 入参缺失或类型不符 | 失败 + 原因 | 否 |
| 白名单不通过 | 失败 + 原因（含被拒的值与维度） | **否** |
| 配置错误（清单格式非法等） | 启动阶段即报错 | — |
| 网络异常 / 超时 | 失败 + 原因 | **是** |
| 外部目标返回 5xx | 失败 + 原因 | **是** |
| 外部目标返回 4xx | 失败 + 原因 | 否 |
| 命令执行超时 | 失败 + 原因；命令被终止 | 否 |

**两个硬约束**：

- 失败结果**不得**被改写成成功；
- 失败**不得**被吞掉导致 Agent 误判任务已完成。

## 4. 审计契约

每次调用（无论成败）都必须写入调用审计，结构沿用既有表，**不新增表、不改表结构**。
审计写入失败**不得**影响业务结果。

## 5. 可独立于模型调用

工具不依赖模型侧能力：单独构造并调用任一工具，应能返回结果或失败结果，便于排查。

## 6. Required Verification

| # | 要求 | 验证方式 |
|---|---|---|
| 1 | 六个内置工具各自"正常能跑通" | 单测：真实临时目录 / 假 HTTP 服务 |
| 2 | 六个内置工具各自"越界被拦下" | 单测：断言失败结果 + **副作用探针为零** |
| 3 | 白名单校验严格早于执行 | 单测：`InOrder` 断言校验先于执行入口 |
| 4 | 校验失败时执行入口调用次数为 0 | 单测：`verify(never())` |
| 5 | 空清单时一律拒绝 | 单测：三维度各一例 |
| 6 | 失败结果的可重试标记与失败类别一致 | 单测：覆盖表中每一行 |
| 7 | 失败的返回值不得是成功 | 单测：断言成功标识为假 |
| 8 | 审计在成败两种情况下都被调用 | 单测：替身审计器断言调用 |
| 9 | 命令超时被终止并返回失败 | 单测：用可控的假命令或注入的时钟 |
| 10 | 默认启用校验（不显式配置开关时仍然拦截） | 单测：不传开关 → 三处仍然抛越界异常 |
| 11 | 显式关闭后三个维度一律放行 | 单测：空清单 + 关闭 → 三处均不抛异常 |
| 12 | 关闭开关不影响配置格式校验 | 单测：关闭 + 空白条目 → 启动阶段仍报错 |

## 7. 总开关（可选关闭校验）

`oryxos.sandbox.enabled` 是**唯一**可以关闭安全边界的入口。

| 项 | 约定 |
|---|---|
| 默认值 | **`true`**（启用） |
| 取值 `false` 的效果 | 三个维度**一律放行**，两个清单内容不再有任何约束力 |
| 关闭时的可观测性 | 启动日志打出**醒目告警**（多行、带分隔线） |
| 与配置格式校验的关系 | **不受影响，始终执行** |

**为什么默认是 `true`**：默认值决定"漏配时的后果"。默认关闭意味着一次配置疏忽就是边界敞开，
这类默认值是安全事故的常见来源；默认开启则最坏情况只是开发时多配几行。

**为什么关闭时仍然校验配置格式**：空白条目是配置**缺陷**，与"当前是否启用"无关。
若只在启用时才校验，问题会在"上线才把开关打开"的那一刻才暴露——那时已经在生产上了。

**为什么用醒目告警**：这条配置最怕的不是"没配"，而是"配了忘记改回来"。
一行普通 INFO 很容易被淹没，多行 WARN 才能让人一眼看见自己正跑在无校验状态。

**边界声明**：该开关只服务于本地开发与调试，**不是**"扩展阶段某能力"的预留，
也**不应**出现在生产环境的配置里。生产环境建议显式写 `enabled: true`，
而非依赖默认值——这样即使有人复制了开发配置，改动也是可见、可评审的。
