## 背景与定位

Provider 让 Agent 会调模型，ReAct 让它会思考，但到现在它还只会"想"和"说"。本特性补的是那双手：
让 Agent 真的去读文件、写文件、跑命令、发 HTTP 请求，以及把业务方自己的外部能力接进来。

工具是"能干事的 Agent"与"会聊天的机器人"之间的分界线。它对内被三类来源共享（OryxOS 内置的、
业务方用 Java 写的、通过外部服务接进来的），对外是 Agent 与真实世界之间唯一的副作用出口——
正因为它能产生副作用，安全边界必须在设计时就串进执行链路，而不是事后补。

**边界声明**：

- 本特性只交付**工具自身的注册、授权、校验与接入**。白名单校验的**执行点**在本特性落地并生效，
  但完整的沙箱体系（三类白名单的统一设计、强制启用、容器级隔离）属后续 Sandbox 特性。
- **不**交付 Memory 的两个工具（`save_memory` / `recall_memory`）——那属 Memory 特性。
- **不**交付 Tool Policy（allow/deny 细粒度规则）、工具按需加载、把 OryxOS 自己变成对外暴露的
  工具服务、一次响应内多工具并行调用。这些都放扩展阶段。
- 本特性**不**新增 Maven 模块。

## 现状与本次要补的缺口

工具相关的**抽象层已经完全就位**（工具接口、执行结果、注册表、执行器、校验与审计钩子），
内置工具类本身也**真实实现**（不是占位）。真正缺的是把它们**接起来**：

| 缺口 | 当前表现 |
|---|---|
| 只有 1 个工具真正可用 | 运行时注册表里只有 `notify`；文件/命令/HTTP 工具虽已实现却没人注册，Agent 根本看不到它们 |
| 白名单校验器从未被装配 | 校验类存在，但没有装配、没有配置来源，实际恒为"未装配"状态，校验链路是空的 |
| 内置工具无法被构造 | 文件/命令/HTTP 工具**强依赖**非空的白名单校验器，不装配就构造不出来 |
| Profile 的工具授权声明是死字段 | 配置里能写 `tools`，但装配 Prompt 时直接取全部工具，声明形同虚设 |
| 外部工具服务能力完全缺失 | 依赖坐标与配置模型在前几轮已铺好，但无任何运行时能力，配置文件也无人读取 |
| 工具清单是"影子清单" | CLI 与 HTTP 两个清单都不读注册表：一个列工作区目录、一个硬编码九个名字，与真实状态不符 |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Agent 能安全地使用内置工具完成实际任务 (Priority: P1)

用户在对话里让 Agent 做事——"读一下这个文件"、"把结果写到那个文件"、"看看目录里有什么"、
"跑一条命令"、"取一个接口的数据"。Agent 自己决定调哪个工具、传什么参数，系统真正执行并把结果递回去。
与此同时，只要涉及越界（路径不在允许范围、命令不在允许清单、域名不在允许清单），
调用必须在**产生任何副作用之前**被拒绝，并明确告诉 Agent 被拒的原因。

**Why this priority**: 这是整节的地基。没有它，Agent 依然只会"想"和"说"，
前面几节交付的 Provider 与 ReAct 循环能力全部落空。有了它，Agent 才算真正能动手。

**Independent Test**: 不依赖模型、不依赖外网。断言启动后六个内置工具都在注册表里；
对每个工具的"放行"与"越界"两条路径分别用真实临时目录 / 真实白名单配置验证，
越界时断言副作用为零（没有读写发生、没有进程被启动、没有网络请求发出）。

**Acceptance Scenarios**:

1. **Given** 应用已启动，**When** 查看工具清单，**Then** 六个内置工具（`read_file`、`write_file`、
   `list_dir`、`shell`、`http_get`、`http_post`）与既有的 `notify` 全部在列。
2. **Given** 允许范围内的一条路径，**When** 调用文件工具读取，**Then** 返回该文件内容。
3. **Given** 允许范围内的一条路径，**When** 调用文件工具写入，**Then** 文件被写入且内容一致。
4. **Given** 允许范围内的一个目录，**When** 调用目录工具，**Then** 返回该目录下的条目列表。
5. **Given** 允许清单内的一条命令，**When** 调用命令工具，**Then** 返回命令输出。
6. **Given** 允许清单内的一个域名，**When** 调用 HTTP 工具，**Then** 返回响应体。
7. **Given** 允许范围**之外**的路径，**When** 调用文件工具，**Then** 返回失败结果并说明路径不在允许范围，
   **且该文件未被读取或写入**（以文件时间戳 / 内容未变为证）。
8. **Given** 允许清单**之外**的命令，**When** 调用命令工具，**Then** 返回失败结果并说明命令未被允许，
   **且没有任何进程被启动**（以副作用探针为证）。
9. **Given** 允许清单**之外**的域名，**When** 调用 HTTP 工具，**Then** 返回失败结果并说明域名未被允许，
   **且没有发出任何网络请求**（以本地假服务零命中为证）。
10. **Given** 越界调用被拒，**When** 查看返回结果，**Then** 该结果标记为**不可重试**——
    越界是配置问题，重试一万次也不会变成允许。
11. **Given** 一个未配置任何白名单条目的新建工作区，**When** 调用任一受白名单约束的工具，
    **Then** 一律被拒绝（默认拒绝，不是默认放行）。

### User Story 2 - 每个 Agent 只能用被授权的那批工具 (Priority: P1)

给 Agent 定义配置时，可以显式列出这个 Agent 允许使用哪些工具。运行到这个 Agent 时，
提供给模型的工具清单**恰好**是声明的那一批：多一个（授权过宽）和少一个（授权过窄）都不算达标。
没有列出的工具，Agent 既看不到、也调不动。

**Why this priority**: 这是核心阶段唯一的工具治理手段。它让"运维助手只给读文件和执行命令、
客服助手只给某个业务接口"变成可配置的一件事，也是把工具能力收窄到最小必要面的前提。

**Independent Test**: 不依赖模型。构造两个声明不同工具清单的 Agent 配置，
断言各自生成的可调用工具集合**恰好等于**声明集合；再构造未声明该字段的配置，断言行为符合约定。

**Acceptance Scenarios**:

1. **Given** 一个显式声明了三个工具的 Agent 配置，**When** 组装这一轮的可调用工具，**Then**
   工具集合恰好是这三个，不多不少。
2. **Given** 两个声明了不同工具清单的 Agent 配置，**When** 分别组装，**Then** 两者集合互不相同
   且各自与自己的声明一致（证明过滤是按 Agent 走的，不是全局一次）。
3. **Given** 一个声明了不存在工具名的 Agent 配置，**When** 组装，**Then** 按"声明集合"处理
   并给出可诊断的提示，不得静默回退成全量。
4. **Given** 一个未声明该字段的 Agent 配置，**When** 组装，**Then** 行为与约定一致（见假设 A-004），
   且该选择在文档中显式可见。

### User Story 3 - 把外部工具服务接进来，且它的失联不拖垮自己 (Priority: P2)

业务方用自己的语言、自己的框架写好一套能力并对外暴露，通过一份声明文件把它登记给 OryxOS。
应用启动时连上去，把它暴露的能力取回来、变成和内置工具一样可被 Agent 调用的工具。
如果这个外部服务没起来、连不上、或者中途挂了，**应用必须照常启动**，只是它的工具不出现；
其它外部服务与内置工具一律不受影响。

**Why this priority**: 这是"业务方零改代码就能扩展能力"的载体，也是后续日报类 Agent 的硬依赖。
但它排在 P2：先把内置能力做扎实，外部接入是增量。

**Independent Test**: 不碰外网。用一个可控的假外部服务：正常时报出工具、异常时抛连接失败。
断言前者被包装注册、可被调用；断言后者只告警、不阻断、"好的服务照常注册"。

**Acceptance Scenarios**:

1. **Given** 声明文件里登记了一个正常的外部服务，**When** 应用启动，**Then** 它报出的能力
   全部出现在工具清单里，且用法与内置工具一致。
2. **Given** 某个外部服务连接失败，**When** 应用启动，**Then** 该次启动**不失败**，
   只产生一条告警，且该服务的工具不出现在清单里。
3. **Given** 同时登记了正常与失联两个外部服务，**When** 应用启动，**Then** 正常那个的工具可用，
   失联那个的不可用，其余内置工具全部可用。
4. **Given** 一个已注册的外部工具，**When** Agent 调用它并传入参数，**Then** 参数被原样转发给外部服务，
   返回值被包装成与内置工具相同的统一结果。
5. **Given** 外部工具调用失败（服务中途挂掉、超时），**When** 返回结果，**Then** 结果标记为**可重试**，
   且失败原因可读（不等于把异常直接抛给 Agent）。
6. **Given** 声明文件不存在或内容为空，**When** 应用启动，**Then** 正常启动，外部工具数为零。

### User Story 4 - 工具清单反映真实状态 (Priority: P3)

想知道"现在到底有哪些工具可用"，无论从命令行还是从 HTTP 接口查，拿到的都必须是**真实注册表**的内容，
而不是一份写死的清单或者一次目录列举。

**Why this priority**: 排查"Agent 为什么不调某个工具"时，这是第一手依据。
当前两个入口都给出与实际不符的答案，会直接误导排查方向。价值明确但不影响主链路，故排 P3。

**Independent Test**: 在受控的注册表状态下（含内置与外部工具、含被 Profile 过滤前后的差异），
断言两个入口返回的名字集合与注册表一致。

**Acceptance Scenarios**:

1. **Given** 应用已启动，**When** 从命令行查看工具清单，**Then** 列出的是注册表中真实存在的工具名。
2. **Given** 应用已启动，**When** 从 HTTP 接口查看工具清单，**Then** 返回与注册表一致的集合。
3. **Given** 某个外部工具服务失联，**When** 查看工具清单，**Then** 该服务的工具不在清单中
   （清单跟随真实状态，不跟随"预期"）。
4. **Given** 注册表为空（无任何工具可用），**When** 查看清单，**Then** 返回明确的空结果说明，
   而不是报错、也不是返回一份非空的硬编码列表。

---

### Edge Cases

- **白名单条目本身格式非法**（相对路径、含通配符的路径、空字符串）：启动时应给出可定位的配置错误，
  而不是留到第一次工具调用时以奇怪的方式失败。
- **工具名重复**（两个来源注册了同名工具）：必须有确定性的处理与可见提示，不能静默让其中一个覆盖另一个。
- **工具入参缺失或类型不符**（调用方给了不存在的字段、或字段类型错误）：
  必须返回可读的失败结果并标记为不可重试，不能让内部类型转换异常冒出去。
- **命令执行超时**：必须终止该命令并返回失败，不能让执行线程挂住。
- **读一个超出允许范围的符号链接**：按解析后的真实路径判定，不能因为链接路径落在允许目录内就放行。
- **工具返回的失败结果一律不得被改写成成功**，也不得被吞掉导致 Agent 以为任务完成了。
- **工具输出过大**（读大文件、命令输出很长）：需要可预期的上限行为，不能让整轮处理被拖垮。
- **未装配模型能力时调用工具**：工具本身应可独立调用（工具执行不依赖模型），便于排查。

## Requirements *(mandatory)*

### Functional Requirements

**工具注册与可用性**

- **FR-001**: 系统 MUST 在启动时把全部内置工具注册进工具注册表。当前只有 `notify` 被注册，
  文件类（`read_file`、`write_file`、`list_dir`）、命令类（`shell`）、HTTP 类（`http_get`、`http_post`）
  必须一并接入，使 Agent 真正可调用。
- **FR-002**: 注册表中的**每一个**工具 MUST 提供非空的名字、描述与参数 schema。
  缺少参数 schema 会让模型无法知道该传什么参数，属致命缺陷，必须有自动化检查兜住。
- **FR-003**: 工具注册表中出现同名工具时，系统 MUST 采取确定性处理并给出可见提示，MUST NOT 静默覆盖。
- **FR-004**: 内置工具的可用性 MUST NOT 依赖模型侧能力：单独构造并调用任一工具应能正常返回结果或失败结果。

**工具授权（Profile 维度）**

- **FR-005**: Agent 每轮组装可调用工具时，MUST 按该 Agent 配置中声明的工具清单过滤，
  使得暴露给模型的集合**恰好等于**声明集合。
- **FR-006**: 过滤 MUST 以"每个 Agent 各自的声明"为粒度，MUST NOT 全局只算一次后复用给所有 Agent。
- **FR-007**: 声明中包含不存在的工具名时，系统 MUST 给出可诊断的提示，MUST NOT 静默忽略该名字、
  MUST NOT 因此回退成全量工具。

**白名单校验（安全边界）**

- **FR-008**: 每个工具在执行前 MUST 完成其适用维度的白名单校验：
  文件类校验路径、命令类校验命令、HTTP 类校验域名。
- **FR-009**: 校验 MUST 严格早于任何副作用；校验不通过时，该次调用 MUST NOT 产生任何文件读写、
  进程启动或网络请求。
- **FR-010**: 校验不通过 MUST 体现为"不可重试"的失败结果，并给出可定位的原因
  （哪一维度、被拒的具体值）。
- **FR-011**: 白名单条目 MUST 支持从配置文件加载，并支持以环境变量占位的方式提供值，
  配置文件中 MUST NOT 出现明文凭证。
- **FR-012**: 白名单条目为空或未配置时，系统 MUST 默认拒绝（fail-closed），
  MUST NOT 默认放行。
- **FR-013**: 白名单条目格式非法时，系统 MUST 在启动阶段给出可定位的错误，
  MUST NOT 留到首次工具调用时才失败。
- **FR-014**: 路径校验 MUST 基于解析后的真实路径进行，MUST NOT 被符号链接或 `..` 绕过。

**失败语义**

- **FR-015**: 工具的失败结果 MUST 携带正确的"可否重试"标记：配置类与白名单类失败不可重试；
  网络异常、超时、外部服务 5xx 可重试。
- **FR-016**: 系统 MUST NOT 把失败结果改写成成功结果，MUST NOT 吞掉失败导致 Agent 误判任务完成。
- **FR-017**: 工具执行 MUST 有可预期的耗时上限；命令类工具超出上限时 MUST 终止该命令并返回失败。

**外部工具服务接入**

- **FR-018**: 系统 MUST 支持通过声明文件登记外部工具服务，声明内容至少包含服务标识、
  传输方式与连接所需信息。
- **FR-019**: 启动时系统 MUST 连接已登记的外部服务、取回其暴露的能力，并包装成与内置工具
  **同等形态**的工具注册进同一注册表，使使用方（含 Agent）无需感知来源差异。
- **FR-020**: 单个外部服务连接失败 MUST NOT 阻断应用启动，也 MUST NOT 影响其它服务与内置工具的注册；
  MUST 只产生一条可定位的告警。
- **FR-021**: 外部工具的调用 MUST 把参数原样转发给外部服务，并把返回值/失败包装成统一结果；
  失败结果 MUST 标记为可重试。
- **FR-022**: 声明文件缺失或内容为空时，系统 MUST 正常启动且外部工具数为零。

**可观测性**

- **FR-023**: 工具清单的两个查询入口（命令行与 HTTP 接口）MUST 返回注册表的真实内容，
  MUST NOT 使用硬编码清单或目录列举替代。
- **FR-024**: 每次工具调用 MUST 写入调用审计（沿用既有审计能力），本特性新接入的工具同样覆盖。
- **FR-025**: 注册表为空时，清单入口 MUST 返回明确的空结果说明，MUST NOT 报错或返回非空假清单。

### Key Entities *(include if feature involves data)*

- **工具（Tool）**：Agent 可调用的一个外部能力。属性：名字（全局唯一，模型据此点名）、
  描述（给模型看）、参数 schema（说明要传什么）、执行结果。不区分来源，来源对其使用方不可见。
- **工具注册表（Tool Registry）**：进程内所有可用工具的汇总。属性：工具集合。
  它是"有哪些工具"的唯一真相来源，清单查询与 Agent 组装都以它为准。
- **工具执行结果（Tool Result）**：一次调用的产出。属性：成功标识、内容、错误信息、可否重试。
  其中的"可否重试"是 ReAct 循环判断"值不值得再试一次"的依据。
- **白名单策略（Sandbox Policy）**：允许的副作用范围。属性：允许的路径清单、允许的命令清单、
  允许的域名清单（支持通配）。空即全拒。
- **工具授权声明（Tool Grant）**：某个 Agent 配置里声明的允许使用的工具名清单。
  未声明时的语义见假设 A-004。
- **外部工具服务声明（External Tool Server）**：业务方登记的一档外部能力来源。
  属性：服务标识、传输方式、连接信息（启动命令/地址）、环境变量。
- **工具调用审计记录（Tool Invocation Audit）**：一次调用的留痕，沿用既有审计结构。
  本特性只保证覆盖，不新增结构。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 应用启动后，工具清单恰好包含 7 个工具（`read_file`、`write_file`、`list_dir`、
  `shell`、`http_get`、`http_post`、`notify`），且清单来源为真实注册表。
- **SC-002**: 越界调用（路径、命令、域名三类各若干用例）被拒绝的比例为 **100%**，
  且每次拒绝前产生的副作用次数为 **0**。
- **SC-003**: 对声明了工具清单的 Agent，暴露给模型的工具集合与声明集合的差异为 **0 个**
  （既无多余、也无缺失）。
- **SC-004**: 在任一外部工具服务不可用的前提下，应用启动成功率 **100%**，
  其余工具可用率 **100%**。
- **SC-005**: 注册表中 **100%** 的工具通过"名字/描述/参数 schema 非空"的检查，
  新增工具会被该检查自动纳入。
- **SC-006**: 失败结果的"可否重试"标记与失败类别一致的用例通过率 **100%**
  （配置/越界类不可重试，网络/超时类可重试）。
- **SC-007**: 工具清单两个入口返回的集合与注册表内容一致，差异为 **0 个**。

## Assumptions

沿用本仓库既有惯例：源文档是**教学示意代码**，与仓库实际架构存在多处差异。
为避免"照着文档写出编译不过的代码"，所有差异与默认取舍在此逐条显式记录。

- **A-001（现状：抽象层已完成）**：工具接口、执行结果、注册表、执行器、前置校验钩子、调用审计钩子
  均**已实现且真实可用**。本特性**不重写**它们，只在既有抽象上补"装配、授权、外部接入、清单"。
- **A-002（现状：内置工具类已实现）**：文件/命令/HTTP 三类内置工具**已有真实实现**，
  且已在执行前调用白名单校验。缺口在**注册**与**校验器装配**，不在工具实现本身。
  → 因此源文档中"用注解标注 Java 方法、启动自动扫描注册"的机制**不采用**：
  仓库惯例是手写实现统一接口 + 在装配处显式登记（既有 `notify` 即此方式），本特性沿用。
- **A-003（现状：白名单校验器无装配）**：校验类已实现，但没有装配、没有配置来源，
  运行期恒为"未装配"。且内置工具**强依赖非空校验器**（缺失即构造失败）。
  → 因此"工具可用"与"白名单生效"**必须一起交付**，不能拆成两个独立增量。
- **A-004（决策：未声明工具授权时的语义）**：Agent 配置中工具清单**未声明或为空**时，视为
  **不限制（全部可用）**，而非"无工具"。理由：与现行为及默认模板一致，避免升级后默认 Agent
  突然失去全部工具能力。
  → **已由使用方确认取此取值**。**代价（显式记录）**：治理上偏弱，忘写清单不会报错。
  若后续希望"空即无工具"，需同步修改默认模板并承担行为变更。
- **A-005（决策：默认拒绝而非默认放行）**：白名单为空时一律拒绝。理由：安全边界的默认方向
  必须是收紧的；放开是显式动作，收紧是默认动作。
  → **代价**：新建工作区不配白名单时，工具全部不可用。这是有意为之，且失败原因必须可读。
- **A-006（范围：不包含 Memory 工具）**：源文档把 `save_memory` / `recall_memory` 也算进
  "内置工具九个"，但它们属 Memory 特性。本特性只接入文件/命令/HTTP 六个，
  加上既有 `notify` 共七个，与 SC-001 对应。
- **A-007（差异：命令工具的平台假设）**：源文档说命令工具执行 `bash` 命令，仓库实现固定走
  Windows 命令解释器。本特性**不改动**该行为（属既有独立缺口），但在文档中显式标注平台假设，
  避免被误读为跨平台可用。
- **A-008（差异：白名单接口形态）**：源文档写作"传入一个动作对象、由沙箱统一裁决"，
  仓库实现是三个按维度划分的校验方法。本特性沿用仓库形态，
  **统一沙箱抽象**（含动作对象、强制启用、容器级隔离）属后续 Sandbox 特性。
- **A-009（差异：外部工具服务的声明结构）**：源文档声明的字段是"传输方式 + 启动命令/环境变量"，
  仓库既有的配置模型是"服务标识 + 地址 + 凭证"。两者不一致，本特性需统一为
  **能同时表达本地子进程与远程两种连接方式**的声明结构，并保证既有解析测试不回归。
  → **外部工具服务已由使用方确认纳入本轮交付范围**，需覆盖连接、包装注册、失联隔离与调用转发全链路。
- **A-010（依赖：外部工具服务的 SDK 已在依赖中声明但从未使用）**：依赖坐标已在前几轮铺好，
  本特性是它第一次被真正使用。本地仓库中存在该版本产物，提供客户端与两种传输实现，
  故**优先复用既有依赖**；若实际能力不足以覆盖两种连接方式，
  则以不引入新第三方依赖为前提改用自实现协议转发，取舍在 plan 阶段定稿。
- **A-011（不变式：副作用仅经工具产生）**：本特性不引入任何绕过工具执行链路的副作用路径；
  所有受白名单约束的副作用都必须经过校验点。
- **A-012（假设：白名单条目由使用方维护）**：工作区内允许什么路径、命令、域名由使用方配置决定，
  本特性只负责"未配置即拒绝"和"配置错误即报错"，不提供可用的默认条目。
