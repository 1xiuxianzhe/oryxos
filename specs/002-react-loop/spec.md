## Clarifications

### Session 2026-09-16

- Q: 规格里说的"最近 N 轮会话历史"，这里的"一轮"具体指什么？ → A: 一次完整往返算一轮（用户提问 → Agent 给出该次最终答复，中间的模型调用与工具执行都算在这一轮内）；默认保留最近 20 次往返。术语上统一用"往返"表示会话历史的单位，用"轮"表示循环的迭代次数。
- Q: 大模型调用失败（超时、限流、返回错误响应）时，这一次用户提问最终应得到什么结果？ → A: 失败上抛并终止本次处理，由入口（CLI/Web）以可读形式展示错误；不切换模型、不做业务级重试，也不用兜底文本把失败伪装成正常答复。
- Q: 一次用户提问的处理是否需要"整体耗时上限"？ → A: 需要。默认 60 秒、可按 Agent 配置覆盖；超时即中止本次处理并按 FR-018 把超时错误上抛，不返回伪装成正常答复的文本。
- Q: 工具调用的审计记录写入失败时，这次工具调用的结果应如何处理？ → A: 审计写入失败不阻断主流程：记录 ERROR 日志后继续返回工具结果（与既有审计实现口径一致）；审计缺失必须显式可见，不得静默。
- Q: 除了把工具调用逐条落库外，是否还需要"一次处理的全过程日志"？ → A: 需要。核心阶段就必须输出结构化日志：处理开始与结束（结束含停止原因与总耗时）、每轮迭代、每次工具调用（工具名/成败/耗时）、异常与超时；日志不得包含密钥、完整系统提示词等敏感内容。验收口径是"仅凭日志即可还原一次处理的轮次、工具与停止原因"（见 FR-021、SC-010）。
- Q: 审计要覆盖到什么粒度？后续要做的后端展示需要看到什么？ → A: 三个粒度都要落库：**请求级**（`agent_runs`，一次提问一条，含用户原始输入、provider/模型、累计 token、轮数、工具调用次数、终态）、**LLM 调用级**（`llm_calls`）、**工具调用级**（`tool_invocations`），三者用 `run_id` 关联，使后端能从一次请求下钻到它的每一次调用。**成功与失败都必须落库**，包括超时、达轮数上限、空响应、模型失败、配置错误；进程中途终止的请求至少留下 `RUNNING` 记录。日志继续保留作为第一现场（FR-021），但处理级追溯不再只依赖日志（见 FR-022、FR-023、SC-011）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 多步任务一次办成 (Priority: P1)

用户提出一个"一句话答不了"的请求（例如"看看今天天气，帮我决定穿什么"）。Agent 不会只回一句敷衍的话，而是自主决定先去查天气、拿到结果、再据此给出穿搭建议，整个过程对用户只表现为"提问一次、得到最终答案"。

**Why this priority**: 这是 ReAct 存在的全部理由。没有它，Agent 只是个一问一答的聊天机器人，无法完成任何需要借助外部信息或分步推进的任务；有了它，Agent 才具备"办事"的能力。Demo 一（每日天气）直接依赖此能力。

**Independent Test**: 给一个需要先获取外部信息才能回答的问题，验证 Agent 确实发起了工具调用、并基于工具返回结果给出了最终答复（而不是把"我想调用某工具"直接当作答复返回）。

**Acceptance Scenarios**:

1. **Given** 用户提出需要外部信息才能回答的问题，**When** Agent 处理该消息，**Then** Agent 先请求调用相应工具，待结果返回后继续推理，最终给出一个不包含工具请求的答复。
2. **Given** 模型一轮就认为可以直接回答（未请求任何工具），**When** Agent 处理该消息，**Then** 立即以该答复结束，不再多转一轮。
3. **Given** 任务需要连续多次工具调用，**When** Agent 逐轮处理，**Then** 后续轮次能够看到前面各轮的模型响应与工具结果，并据此推进。
4. **Given** 模型请求调用多个工具，**When** Agent 执行，**Then** 这些工具被依次执行，结果全部回填后再进入下一轮。

---

### User Story 2 - 卡住时能停下来 (Priority: P2)

模型有时会反复要求调用工具却不收敛。用户（以及运维者）需要确信这种情况不会无休止地消耗下去，而是会在一个明确的上限内停止，并给出让人看得懂的提示。

**Why this priority**: 防止"死循环"烧钱、拖死请求，是最基本的可用性底线。缺少它，一个坏提示词或坏模型行为就能把系统拖垮。

**Independent Test**: 让模型在每一轮都返回工具请求，验证处理在一个固定轮数上限后停止，且返回可识别的收尾提示。

**Acceptance Scenarios**:

1. **Given** 模型每一轮都请求调用工具、永不收敛，**When** Agent 处理，**Then** 在达到轮数上限时停止，且恰好执行的轮数不超过上限。
2. **Given** 某 Agent 在其配置中覆盖了轮数上限，**When** Agent 处理，**Then** 使用该配置值；**Given** 未覆盖，**Then** 使用默认上限 10。
3. **Given** 因达到上限而停止，**When** 用户收到结果，**Then** 结果中包含明确的"已达到最大轮数"类提示，而不是被伪装成正常答案。
4. **Given** 单次处理的累计耗时超过了配置的整体耗时上限，**When** 处理仍在进行，**Then** 立即中止本次处理，并按 FR-018 把超时错误上抛给入口（不返回伪装成正常答复的文本）。

---

### User Story 3 - 过程可追溯、会话可延续 (Priority: P3)

使用者和运维者事后需要能回答"这次 Agent 到底做了什么、调了哪些工具、成没成、为什么失败"。同时，一次处理结束后会话历史必须被保存，重启后还能接着聊。

**Why this priority**: "可审计"是 OryxOS 的差异化卖点。审计与持久化放在核心阶段做，能避免后期从日志反解析返工；但相对"能跑通"而言优先级次之。

**Independent Test**: 执行一次包含工具调用的处理，随后查询审计记录与会话历史，验证两者都能还原本次处理的关键信息（含失败场景）。

**Acceptance Scenarios**:

1. **Given** 一次成功的工具调用，**When** 执行完成，**Then** 存在一条标记为成功、包含工具名与耗时的调用记录。
2. **Given** 工具执行失败或工具不存在，**When** 执行完成，**Then** 存在一条标记为失败且带有错误原因的记录，并且该失败不会中断整个处理（错误结果被回填，循环继续）。
3. **Given** 一次处理结束（无论成功还是抛异常），**When** 处理返回，**Then** 该会话的完整历史已处于持久化状态。
4. **Given** 完成过一次多轮处理，**When** 事后查看会话，**Then** 每一轮的模型响应与工具结果都能被看到，顺序与发生顺序一致。
5. **Given** 某个用户请求以任一方式结束（成功、达轮数上限、空响应、超时、模型失败或配置错误），**When** 事后按时间或会话查询请求级审计，**Then** 都能查到这条请求，并能直接读到"问了什么、用的哪个模型、花了多少 token、跑了几轮、成没成、没成为什么"。

---

### User Story 4 - 人格与技能即改即生效 (Priority: P4)

运营者直接编辑 Agent 的角色设定、启动信息与技能文件（`.oryxos/` 下），不希望还要重启系统才能生效；同时，如果配置里显式引用的文件写错了名字或漏了文件，希望立刻被发现，而不是"人格悄悄丢了"。

**Why this priority**: 直接影响调优效率与故障可发现性，属于体验与可靠性增强；不影响主链路跑通，故排在最后。

**Independent Test**: 修改一个技能/启动文件后再次处理消息，验证模型收到的输入内容已包含新内容；再故意引用一个不存在的文件，验证会报错或告警。

**Acceptance Scenarios**:

1. **Given** 运营者修改了某 Agent 引用的技能或启动文件，**When** 下一次组装模型输入，**Then** 使用的是修改后的内容（不需要重启）。
2. **Given** Agent 配置中显式引用了某个技能文件但该文件不存在，**When** 组装模型输入，**Then** 以明确的错误终止本次组装（不静默跳过）。
3. **Given** 启动信息文件缺失，**When** 组装模型输入，**Then** 至少记录一条告警，处理继续进行。
4. **Given** 组装模型输入，**Then** 其中包含当前日期与时间，使模型能够理解"今天"的含义。

---

### Edge Cases

- 模型返回既没有文本、也没有工具请求（空响应）时：以明确提示结束本次处理，不继续空转（见 FR-016）。
- 工具执行抛出异常或返回失败结果时：循环继续，失败信息以 `tool` 角色消息回填进会话（含错误原因）。
- 模型给出的工具参数不是合法结构化数据时：不崩溃，降级为一条失败的工具结果并回填（见 FR-008）。
- 会话历史超过 20 次往返上限时，按"最旧的完整往返先丢弃"处理；角色与启动设定、长期记忆属于独立组成部分，不参与截断（见 FR-011、FR-012）。
- 模型一次请求多个工具时：某个工具失败不影响其余工具执行，其余结果照常全部回填后再进入下一轮（见 FR-007）。
- 处理过程中抛出异常时："当前 Agent 上下文"在 `finally` 中被清理，不会跨请求泄漏（见 FR-010）。
- 请求的 Agent 配置（Profile）不存在时：抛出 `AgentConfigurationException` 并上抛给入口，不返回空答案。
- 大模型调用失败（超时、限流、错误响应）时：终止本次处理并把错误上抛给入口展示，不产生"看似正常"的答复（见 FR-018）。
- 单次处理累计耗时超过整体上限（默认 60 秒）时：立即中止本次处理，并把超时错误按 FR-018 上抛给入口展示（见 FR-019）。
- 审计写入失败（如存储暂时不可用）时：不阻断主流程，记 ERROR 日志后继续返回工具结果；审计缺失不得静默（见 FR-020）。
- 请求级审计记录停在"进行中"（进程被 kill / 断电 / 部署重启）时：视为可追溯的异常终局——后台据此能看出"这次请求没有正常结束"，而不是当作"从未发生过"（见 FR-022）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 对每条用户消息驱动一个"推理—行动—观察"循环，直到模型给出不含工具请求的答复，或达到轮数上限。
- **FR-002**: 系统 MUST 在每轮把当前可用的工具说明提供给模型，并能接收模型返回的工具调用请求。
- **FR-003**: 当模型返回答复且未请求任何工具时，系统 MUST 立即结束循环并返回该答复。
- **FR-004**: 系统 MUST 限制单次处理的最大轮数，默认值为 10，且必须支持按 Agent 配置覆盖。
- **FR-005**: 达到轮数上限仍未收敛时，系统 MUST 停止并向用户返回明确的提示信息。
- **FR-006**: 系统 MUST 把每轮的模型响应与工具执行结果累积进该会话的历史记录。
- **FR-007**: 系统 MUST 按顺序执行模型在单轮内请求的所有工具调用（核心阶段不做并行执行）。
- **FR-008**: 系统 MUST 为每一次工具调用记录审计信息：成功时标记成功并记录耗时；失败时标记失败并记录错误原因。审计过程 MUST NOT 吞掉或改写"工具调用自身"的原始异常（工具失败必须原样反映为失败结果，不得因审计动作而吞掉或改写）；审计**写入**失败的处理口径见 FR-020。
- **FR-009**: 系统 MUST 在单次处理结束时持久化该会话的历史记录——**无论成功还是失败（含超时、模型失败、内部错误）**，处理结束时机与 `AgentContext` 清理时机一致（`finally`），使已累积的会话历史不会因异常而整段丢失。
- **FR-010**: 系统 MUST 让工具执行期间能够获知"当前正在处理的 Agent 配置"，并且 MUST 在单次处理结束（包括异常结束）后清理该上下文。
- **FR-011**: 组装模型输入时，系统 MUST 按固定顺序包含：角色与启动设定、长期记忆（若 MemoryReader 可用且返回非空；否则该部分为空且不产生任何消息，不影响其余三部分）、最近的会话历史、当前可用工具列表。
- **FR-012**: 系统 MUST 只向模型提供最近的 N 次完整往返（一次往返 = 用户提问 → Agent 给出该次最终答复，含期间的模型调用与工具执行），超出部分按"最旧的先丢弃"淘汰；默认 N 为 20，且必须支持配置。角色与启动设定、长期记忆属于独立组成部分，不参与该截断（见 FR-011）。
- **FR-013**: 系统 MUST 在角色与启动设定部分附上当前日期与时间。
- **FR-014**: 系统 MUST 在每次组装模型输入时重新读取技能与启动文件，不使用缓存内容（即每次组装都重新读取文件内容，不做任何进程内内容缓存，包括按修改时间缓存）。
- **FR-015**: 当 Agent 配置显式引用的技能文件缺失时，系统 MUST 报错；当启动信息文件缺失时，系统 MUST 至少记录告警并继续。
- **FR-016**: 模型返回既不包含文本、也不包含工具请求时，系统 MUST 以明确提示结束该轮，而不是继续空转。
- **FR-017**: 外部调用（大模型、工具）在每次处理中都 MUST 携带所属会话标识，以便审计记录与会话关联。
- **FR-018**: 当大模型调用失败（超时、限流、错误响应等）时，系统 MUST 终止本次处理并把错误上抛给调用入口，由入口负责以可读形式呈现给用户；MUST NOT 返回兜底文本把失败伪装成正常答复，也 MUST NOT 在核心阶段切换其他模型或做业务级重试。
- **FR-019**: 系统 MUST 为单次处理设置整体耗时上限，默认 60 秒，且 MUST 支持按 Agent 配置覆盖；一旦超时，MUST 立即中止本次处理并按 FR-018 把超时错误上抛给入口，MUST NOT 将其转为看似正常的答复。
- **FR-020**: 审计写入失败 MUST NOT 阻断主流程：系统 MUST 记录 ERROR 日志后继续返回工具结果；审计缺失 MUST 显式可见，MUST NOT 静默丢弃。
- **FR-021**: 系统 MUST 在单次处理的关键节点输出结构化日志——处理开始与结束（结束日志 MUST 含停止原因与总耗时）、每轮迭代、每次工具调用（工具名、成败、耗时）、异常与超时；日志 MUST 足以还原一次处理的轮次、工具与停止原因，且 MUST NOT 记录密钥、完整系统提示词等敏感内容。
- **FR-022**: 系统 MUST 为每一次处理（一次用户请求）落一条请求级审计（`agent_runs`），字段至少包含：用户原始输入、provider 与模型、累计 token 用量、循环轮数、工具调用次数、开始与结束时间、终态（成功 / 达轮数上限 / 空响应 / 超时 / 模型失败 / 配置错误 / 内部错误）与失败原因。MUST 采用**两阶段写入**：处理开始先落一条进行中记录，处理结束（含失败）更新为终态——使进程中途被终止的请求也能被查到，而不是毫无痕迹。
- **FR-023**: 系统 MUST 让每次 LLM 调用与每次工具调用的审计记录携带所属请求的标识（`run_id`），使后台能够从一次请求下钻到它的全部模型调用与工具调用；不在处理上下文中发生的调用（如直接调用 Provider）MUST 照常落库，`run_id` 置空即可，MUST NOT 因缺少关联而丢弃记录。

### Key Entities *(include if data involved)*

- **Session（会话）**: 一次对话的上下文容器，包含会话标识、所属 Agent 配置名、来源渠道、用户标识、按序排列的消息列表、状态与时间戳。
- **Message（消息）**: 会话中的一条往来记录，包含角色（用户/助手/工具）与内容。
- **Profile（Agent 配置）**: 定义一个 Agent 的行为，含所用模型与参数、可用工具、技能与启动信息、最大轮数（迭代上限）、历史往返上限、单次处理整体耗时上限等。
- **ToolCall（工具调用请求）**: 模型在响应中提出的调用意图，包含工具名与参数。
- **ToolResult（工具结果）**: 一次工具执行的结果，包含成功标记、内容、错误信息与是否可重试。
- **ToolInvocation（工具调用审计）**: 一次工具调用的落库记录，包含所属会话与所属请求（`run_id`）、工具名、入参、结果、状态（SUCCESS/FAILED）与成功标记、错误原因、耗时与时间戳。
- **AgentRun（请求级审计）**: 一次处理（一次用户提问）的落库记录，包含用户原始输入、所属会话与来源渠道、Agent 配置名、provider 与模型、累计 token、循环轮数、工具调用次数、进行中/终态标记、停止原因、失败原因与起止时间。
- **AgentContext（当前 Agent 上下文）**: 单次处理期间可被工具读取的"当前 Agent 配置"载体，生命周期与一次处理严格对齐。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 需要使用外部信息、原本要用户分多步引导的任务，可在一次提问内自动完成并给出最终答复。
- **SC-002**: 面对持续请求工具的异常模型行为，单次处理必定在 10 轮内结束，不会无限消耗。
- **SC-003**: 100% 的工具调用（无论成功还是失败）事后都能被查询到；失败记录 100% 包含失败原因。
- **SC-004**: 一次处理结束后，会话历史的保存率为 100%，进程重启后仍可读取。
- **SC-005**: 修改技能/启动文件后，下一次提问即生效，无需重启。
- **SC-006**: 上述全部验收点在无网络依赖的自动化测试中覆盖；harness 单测（不触网、不连真实模型）总时长不超过 30 秒，全量 `mvn test` 在分钟级内完成。
- **SC-007**: 达到轮数上限时，返回文本中 100% 包含"已达到最大轮数"字样及实际轮数，用户可据此明确区分于正常答案。
- **SC-008**: 单次处理的整体耗时不会超过所配置的上限（默认 60 秒）；超时发生后，本次处理必定已被中止，且调用方能看到明确的超时错误。
- **SC-009**: 审计存储故障期间，Agent 仍能正常完成处理（可用性不受影响）；同时审计缺失 100% 会留下可被运维发现的错误记录，不会静默消失。
- **SC-010**: 对任意一次已完成的处理，仅凭日志即可还原"转了几轮、调用了哪些工具、各步耗时、因何停止"，无需查询审计表或二次复现。
- **SC-011**: 100% 的用户请求（无论成功、达轮数上限、空响应、超时、模型失败还是配置错误）都能在 `agent_runs` 中查到，且请求内容、所用 provider 与模型、token 用量、轮数、工具调用次数与失败原因均可直接读取；进程中途被终止的请求至少留下一条进行中记录。

## Assumptions

- 依赖"能力一：对接 LLM"已交付；本能力通过它调用大模型，不重复处理 Provider 差异。
- 需要一个可被调用的工具抽象与工具注册机制；本能力负责"调度与执行"，具体内置工具及其实例装配由后续能力提供（本特性交付时注册表为空属预期）。
- 外部触发源（CLI / Web / 定时）的接入属通道能力（能力五）；本能力只交付统一入口 `AgentService`，不实现具体通道，验收通过直接调用该入口的集成用例完成。
- 会话与审计的存储沿用项目既有的持久化方案；审计在核心阶段就要写入（查询接口可后置）。
- 核心阶段明确不做：工具并行调用、Agent 之间互相委托、流式输出、上下文动态压缩；上下文先用"只保留最近 N 轮"的简单策略。
- 默认值取业界常见做法：最大轮数（循环迭代次数）10 次、历史保留 20 次完整往返、单次处理整体耗时上限 60 秒，均可被 Agent 配置覆盖。
- 当模型一轮既无文本也无工具请求时，视为无效响应，返回明确提示并结束本次处理。
- 沙箱/白名单校验的具体规则由后续 Sandbox 能力定义；本能力保证"工具执行前必经校验"这一位置存在。
- 单次处理在单线程内完成；并发场景下同一"当前 Agent 配置"上下文不会跨请求泄漏。
- Bootstrap 三件套默认指工作区下的 `.oryxos/AGENTS.md`、`.oryxos/SOUL.md`、`.oryxos/USER.md`（可被 Profile 的 `bootstrap.files` 显式覆盖）。
